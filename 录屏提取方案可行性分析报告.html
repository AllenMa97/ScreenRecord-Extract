一、执行摘要与总体判定

总体判定
方案在工程层面可实行，技术路线选型正确。采用"CPU-friendly 经典CV算法 + CNN base + API服务"的路线契合算力约束，异步流水线架构（视频IO → 视觉处理 → OCR → 业务后处理）的线程解耦设计规范。三层去重漏斗（帧差过滤 → 拉普拉斯模糊过滤 → pHash视觉去重 → 文本编辑距离去重）的逻辑链完整，能覆盖大部分滚动场景。

但经过与顶会文献的交叉验证，方案存在 6个需要在落地前解决的关键风险，其中2个可能导致内容丢失（高严重度）。核心矛盾在于：方案的每一步单独看都合理，但串联后的鲁棒性瓶颈出现在几个容易被忽视的环节——尤其是 pHash 在文本密集型UI上的区分度问题，以及快速滑动导致的内容空洞问题。

核心结论速览

模块可行性关键问题
自适应抽帧（帧差T1/T2）可行阈值需按设备分辨率标定；三态采样逻辑正确
ROI锁定与追踪可行概念需澄清：ROI是屏幕视口而非内容区域，无需追踪内容位移
拉普拉斯模糊过滤基本可行阈值对文本密度敏感，需归一化；纯文本区可能误判
pHash视觉去重高风险文本密集UI布局高度相似，不同滚动位置pHash距离可能<5导致误丢弃
文本级去重与LCS拼接基本可行整帧文本比对脆弱；应改为逐文本行/块跟踪
时序状态机（SUSPEND/RESUME）基本可行有顶会先例（Agent-SAMA），但恢复率仅71.9%，anchor匹配需强化
异步流水线架构可行Ring Buffer + 无锁队列设计规范

二、相关顶会论文调研

以下论文按与方案的相关性排序，覆盖四个核心方向：移动UI状态机建模、视频关键帧提取、视频文本检测与跟踪、移动UI理解。

2.1 移动UI状态机建模 — 直接验证"时序状态机"思路

Agent-SAMA: State-Aware Mobile Assistant [1]

arXiv:2505.23596, 2025 | 框架：FSM + 多Agent协作

这是目前最直接验证方案"时序状态机"思路的工作。Agent-SAMA 将移动App执行建模为有限状态机（FSM）——UI屏幕映射为状态，用户操作映射为状态转移。其核心贡献与方案的对应关系：

  • 状态建模：每个UI screen = 一个状态节点，附带前置条件、后置条件、下一状态预测。方案中的 NORMAL/SUSPENDED/RESUMING 状态枚举与此一致。
  • 异常检测：通过比对"预测状态"与"实际状态"判断是否偏离。方案中的"UI布局一致性校验"对应此机制。
  • 恢复机制：Reflection Agent 负责错误恢复。在 Mobile-Eval-E benchmark 上，恢复成功率 71.9%，任务成功率 84.0%。
关键启示
Agent-SAMA 的恢复率仅 71.9%，说明状态恢复本身就是难题。方案的"断点续传"机制不能假设100%成功，必须有降级策略（如：恢复失败时标记内容缺口，而非强行拼接）。

2.2 视频关键帧提取 — 验证"自适应抽帧"思路

Adaptive Keyframe Sampling (AKS) [2]

CVPR 2025 | arXiv:2502.21271

将关键帧选择形式化为优化问题，目标函数同时优化两个维度：(1) 关键帧与查询的相关性 (2) 关键帧对视频的覆盖度。这揭示了方案的一个盲区——方案的帧差+拉普拉斯+pHash优化的是"相关性"（是否有变化、是否清晰），但没有显式优化"覆盖度"（是否捕获了所有内容）。当快速滑动导致中间帧全部被模糊过滤丢弃时，覆盖度受损。

KeyVideoLLM [3] / K-frames [4] / DATE [5]

arXiv:2407.03104 / CoRR 2025 / arXiv:2509.09263

工作核心方法对方案的启示
KeyVideoLLM文本-视频帧相似度选择关键帧，压缩率60.9×验证了相似度去重路线的有效性；但方案用pHash而非CLIP相似度，更轻量也更容易在文本UI上失效
K-frames场景驱动+任意数量关键帧，保持时序连续性强调"时序连续性"——方案丢弃模糊帧后可能产生时序断裂
DATE两阶段采样：语义对齐 + 时间正则化贪婪采样两阶段思路可借鉴：先粗筛（帧差）再精筛（pHash/文本）

2.3 视频文本检测与跟踪 — 方案缺失的关键模块

End-to-End Video Text Detection with Online Tracking [6]

Pattern Recognition, 2021 | 首个端到端视频文本检测+在线跟踪框架

这是视频OCR领域最直接相关的工作。其核心思想：不要把每帧OCR结果当作孤立文本，而要跟踪文本实例在帧间的对应关系。使用外观+几何+PHOC特征构建可解释描述子，在ICDAR 2013 Video等benchmark上达到SOTA。

方案缺口
方案将整帧OCR文本作为一个整体进行Levenshtein比对，缺少逐文本行/块的跟踪。视频文本跟踪文献表明：跟踪单个文本实例（通过bounding box IoU + 文本相似度 + 外观特征）远比整帧比对鲁棒。这是方案最重要的改进点。

Video OCR Pipeline（工业实践总结）[7]

CodeSOTA 技术文档

标准视频OCR流水线为：Frame Selection → Text Detection → Recognition → Tracking → Deduplication → Temporal Consistency。其中文本跟踪的四种方法：

跟踪方法原理复杂度适用场景
Bounding Box IoU帧间文本框重叠度低静态文本（字幕、UI）
Text Similarity识别文本内容匹配中位置变化但内容稳定
Embedding Distance视觉嵌入向量匹配高字体/样式变化
Optical Flow光流预测文本区域运动高移动文本

对于手机录屏场景，Bounding Box IoU + Text Similarity 的组合是最契合的——UI文本位置相对固定，内容稳定，且计算开销低。

2.4 移动UI理解与关键帧过滤

GUITrans2Act / Teach VLM [8]

arXiv:2606.12817, 2026 | 荣耀 + CUHK

该工作从手机操作演示视频中提取操作关键帧，明确指出："演示视频包含密集帧，其中穿插着任务无关的视觉噪声（如加载动画和过渡效果）"。这与方案面临的"滑动拖影、转场动画"问题完全一致。其解决方案是过滤无关过渡帧，提取操作相关关键帧——验证了方案"拉普拉斯过滤+视觉去重"的必要性。

Ferret-UI [9]

ECCV 2024 | Apple Research

针对移动UI屏幕的MLLM，采用"any resolution"策略处理UI屏幕的细长纵横比和小目标。虽然方案约束不用VLM，但Ferret-UI的发现对ROI设计有参考价值：UI屏幕的文本/图标目标远小于自然图像，需要在ROI裁剪时保留足够分辨率（不建议过度降采样）。

三、方案逐节可行性分析

3.1 自适应抽帧（帧差阈值 T1/T2）— 可行

评估结论

设计正确，阈值建议合理。三态采样（静止低频 / 滑动中频 / 剧烈变化高频）的逻辑链完整，与视频摘要领域的帧差法一致 [13]。

具体分析

  • T1=3~5, T2=20~30（8-bit灰度MAE）：合理。但需注意：resize到160×120或80×60后，单像素差异被平均化，MAE值更稳定。建议在resize后的尺寸上标定阈值，而非直接套用全分辨率经验值。
  • 计算优化：灰度+resize+ROI裁剪后计算MAE，单次耗时微秒级，CPU友好，无异议。
  • 潜在问题：帧差法检测的是"像素变化量"，但无法区分"内容滑动"与"光照/闪烁变化"。手机录屏中，键盘弹出的动画、通知栏消息推送等都会产生帧差，但不代表聊天内容变化。建议在帧差触发后，增加一步轻量级UI布局校验（如：检测ROI区域内是否有预期的文本行结构），避免对无关变化高频采样。

3.2 ROI锁定与追踪 — 可行，需澄清概念

概念澄清

方案中有一处表述需要澄清："如果用户滑动导致内容移动，由于我们是在ROI内部做帧差和OCR，外部的滑动不会影响ROI的边界"——这里的ROI应理解为"屏幕上的固定视口区域"（如：去掉状态栏和导航栏后的中间区域），而非"内容区域"。内容在ROI内部滚动，ROI边界固定。这个理解是正确的。

关键点：ROI定义的是"在哪里看"，而不是"看什么内容"。因此：

  • 初始化阶段定位ROI（剔除状态栏、导航栏、悬浮窗）：可行，用边缘检测+连通域分析或轻量级目标检测均可。
  • 后续帧无需重新检测ROI：仅在检测到全屏UI变化时重新检测。正确。
  • 每5秒校验ROI边界：合理的防漂移措施。
注意
ROI裁剪后送入OCR的分辨率要足够。Ferret-UI [9] 的研究表明UI文本目标小，过度降采样（如直接缩到320×240）可能导致小字号文字丢失。建议ROI裁剪后保留原始分辨率，仅在计算帧差/拉普拉斯时降采样，OCR使用原图或轻度降采样。

3.3 拉普拉斯模糊过滤 — 基本可行，需归一化

评估结论

拉普拉斯方差是模糊检测的经典方法 [10]，方案选用正确。但阈值设定存在内容敏感性风险。

具体分析

  • 阈值30~50（1080p）：文献 [10] 表明8-bit灰度图常用阈值约100。方案设30~50偏保守（只拦截严重模糊）。但方案目标是"过滤掉90%无效滑动帧"，保守阈值可能导致中度模糊帧漏网，送入OCR后产生低质量文本。
  • 内容敏感性问题：拉普拉斯方差反映的是"高频边缘能量"。一帧充满密集小字文本的聊天记录，即使略有模糊，Score也可能高于50；而一帧只有少量大字的内容，即使清晰，Score也可能低于100。阈值需要按文本密度归一化。
  • 改进建议：不设绝对阈值，改为相对阈值——维护一个滑动窗口的Score基线（如最近10个"清晰帧"的平均Score），当前帧Score低于基线的30%才判定模糊。这样自适应不同内容密度。

3.4 pHash视觉去重 — 高风险，最大瓶颈

评估结论

pHash是近重复检测的主流方法 [11][12]，方案选用方向正确。但在"文本密集型UI"场景下存在严重的区分度不足风险，这是整个方案最关键的薄弱环节。

问题分析

pHash的原理是将图像缩放到32×32，做DCT，取8×8低频分量生成64-bit哈希。这意味着pHash捕获的是图像的低频结构（整体明暗布局）。对于聊天记录UI：

  • 同一App的聊天界面，不同滚动位置的整体布局高度相似（顶部标题栏、中间消息列表、底部输入框的结构一致）。
  • 低频分量主要反映这些结构性布局，而非具体文字内容。
  • 因此，两个不同滚动位置的聊天页面，pHash汉明距离可能<5，被方案误判为"重复"而丢弃。
严重风险
这意味着在连续滚动场景中，pHash去重可能丢弃大量"内容不同但布局相似"的有效帧，导致大面积内容丢失。这不是参数调优能解决的，而是pHash算法本身在该场景下的固有局限。

改进方案

  1. 增大哈希位数：从64-bit（8×8 DCT）升级到256-bit（16×16 DCT），捕获更多中频信息，提升对文本排版的区分度。
  2. pHash + 局部特征组合：pHash判断布局变化，同时计算ROI内若干局部区域（如将ROI分成4×4网格，每格单独算pHash）的哈希，只有当所有局部哈希都相似时才判定重复。
  3. 降级为文本级去重为主：承认pHash在文本UI上的局限，将pHash作为"粗筛"（距离>15直接保留），距离<15的帧不丢弃，而是送入OCR后用文本相似度做最终判定。代价是OCR调用量增加，但避免了内容丢失。
  4. 考虑dHash辅助：dHash（差值哈希）对梯度方向敏感，对文本行的方向性变化比pHash更敏感 [12]。

3.5 文本级去重与LCS拼接 — 基本可行，应改为逐行跟踪

评估结论

编辑距离去重的思路正确，相似度阈值（>0.85丢弃，0.5~0.85用LCS拼接）合理。Myers' diff优化长文本的建议专业。但整帧文本比对的范式存在鲁棒性问题。

问题分析

  • 整帧比对脆弱：将一帧所有OCR文本拼接为一个字符串再算编辑距离，任何一个文本行的OCR错误都会影响整体相似度。例如：10行文本中1行OCR出错，相似度可能从0.95降到0.85，触发不必要的拼接逻辑。
  • LCS拼接对OCR错误敏感：LCS要求精确子序列匹配，OCR错一个字就断链。视频文本跟踪文献 [6] 表明，应使用模糊匹配+置信度加权而非精确LCS。
  • 缺少空间信息利用：OCR结果包含每个文本框的坐标。整帧比对丢弃了空间信息，而这些信息对于判断"哪些行是新的、哪些行是旧的"至关重要。

改进方案（借鉴视频文本跟踪 [6][7]）

将OCR结果按文本行/块组织，每行包含 (text, bbox, confidence)，然后：

  1. 逐行跟踪：用 Bounding Box IoU + 文本相似度组合，将当前帧的文本行与上一帧的文本行匹配。
  2. 行级去重：匹配成功的行（IoU>0.5且文本相似度>0.9）视为同一行，丢弃或更新；未匹配的行视为新内容。
  3. 行级拼接：对部分重叠的行（如滚动导致一行被截断），用编辑距离做行内拼接，而非整帧拼接。
  4. 时序一致性投票：同一文本行在连续N帧中被多次识别，用多数投票 + 置信度加权纠正OCR错误 [7]。

3.6 时序状态机（SUSPEND/RESUME）— 基本可行，有顶会先例

评估结论

状态机设计有Agent-SAMA [1] 的顶会先例支撑，思路正确。NORMAL/BLUR_MOVING/SUSPENDED/RESUMING 四态设计合理。但挂起/恢复的触发逻辑和anchor匹配机制需要强化。

问题分析

  • 挂起触发逻辑：方案用"连续10帧拉普拉斯分数<30 + 边缘特征骤降80%"触发挂起。但低拉普拉斯分数=模糊=正在滑动，而非退出。应改为直接检测UI布局变化——如：ROI区域是否出现预期的聊天列表结构（可用轻量级分类器或模板匹配），而非从模糊度间接推断。
  • 恢复时的anchor匹配：方案说"提取当前页面的锚点特征与挂起前缓存上下文匹配"。但用户返回时可能滚动到了不同位置（不是挂起前的同一位置）。anchor匹配需要支持部分匹配（如：至少有一行文本匹配即认为回到同一页面），而非完整匹配。
  • Agent-SAMA的启示：其恢复率71.9% [1]，意味着约28%的情况下状态恢复失败。方案应设计降级策略：恢复失败时，将挂起前后的内容标记为"断开"（gap），而非强行拼接，避免错误拼接污染结果。

改进建议

引入一个轻量级UI页面分类器（小型CNN或MobileNet变体），专门判断当前帧属于"聊天记录页/参数页/桌面/设置页/其他"五类。这个分类器的输出直接驱动状态机：

if page_class == "chat_page" and state == SUSPENDED:
    state = RESUMING  # 尝试恢复
elif page_class != "chat_page" and state == NORMAL:
    state = SUSPENDED # 挂起

这比"从拉普拉斯+边缘特征间接推断"更直接、更可靠，且分类器推理开销可控（MobileNet在CPU上约5-10ms/帧）。

3.7 异步流水线架构 — 可行

评估结论

架构设计规范，无异议。Ring Buffer防内存溢出、无锁队列线程通信、IO与计算线程隔离，都是标准工程实践。

优化建议

  • Queue容量自适应：Queue 2（候选关键帧）的容量不应固定，应根据OCR处理速度动态调节。如果OCR跟不上，Queue 2溢出时应丢弃最旧的帧（而非阻塞），并记录丢弃日志。
  • OCR批处理：Thread 2 不必逐帧送OCR，可攒批（如4-8帧）后批量送PaddleOCR API，减少API调用开销。
  • 背压机制：当Queue 3积压时，应向Thread 1反馈，降低抽帧频率（反压），而非让队列无限增长。

3.8 异常兜底策略 — 基本可行

评估结论

纯色检测（桌面背景）和最长公共子序列（LCS）拼接的思路可行。但LCS拼接的鲁棒性问题同3.5节——应改为逐行模糊匹配。

"长文本截断拼接"场景的更优方案：利用OCR的bbox坐标，判断某行是否在ROI边界处被截断（bbox顶部或底部超出ROI边界）。被截断的行与相邻帧的对应行做编辑距离匹配拼接，这比全文LCS更精准。

四、六大关键风险

风险1：pHash在文本UI上的区分度不足 高

不同滚动位置的聊天页面布局高度相似，pHash距离可能<5导致误丢弃。可能导致大面积内容丢失。

缓解：增大哈希位数 / 局部pHash / pHash仅作粗筛，文本相似度做终判

风险2：快速滑动导致内容空洞 高

滑动太快时，所有中间帧被拉普拉斯过滤。若两次停止位置无内容重叠，中间内容永久丢失。方案的覆盖度未显式保障（AKS [2] 指出覆盖度是关键维度）。

缓解：滑动停止后，检测与上一有效帧的文本重叠率；若重叠率<30%，标记为"内容缺口"

风险3：缺少逐文本行跟踪 中

整帧文本比对脆弱，OCR单行错误影响整体相似度。视频文本跟踪文献 [6][7] 表明逐实例跟踪远更鲁棒。

缓解：按bbox+text组织OCR结果，逐行匹配去重与拼接

风险4：状态恢复成功率不达标 中

Agent-SAMA [1] 恢复率仅71.9%。方案的断点续传不能假设100%成功。

缓解：恢复失败时标记gap而非强拼；引入UI页面分类器替代间接推断

风险5：拉普拉斯阈值内容敏感 中

绝对阈值30-50对文本密度敏感，密集小字区可能漏判模糊。

缓解：改为相对阈值（滑动窗口基线的百分比）

风险6：OCR时序一致性未利用 中

同一文本行在连续帧中被多次识别，方案未利用多帧投票纠错。Video OCR [7] 的时序一致性投票可提升3-5%准确率。

缓解：对跟踪到的文本行做多帧多数投票+置信度加权

五、改进算法方案设计

在原方案基础上，针对上述风险提出改进。改进遵循"CPU-friendly"约束，不引入VLM，新增模块均为轻量级。

5.2 关键改进点详解

改进1：UI页面分类器替代间接状态推断

新增一个轻量级CNN分类器（MobileNetV3-Small或更小的自定义CNN），输入ROI裁剪图（降采样到224×224），输出5类页面类型。这个分类器在Thread 1b中运行，每帧推理约5-10ms（CPU），直接驱动状态机：

  • 分类为"聊天页/参数页" → 状态机保持NORMAL，继续处理
  • 分类为"桌面/设置/其他" → 状态机进入SUSPENDED
  • SUSPENDED状态下分类恢复为"聊天页/参数页" → 进入RESUMING

训练数据可从公司现有的截图OCR任务中采集（已有标注的截图数据），无需额外标注成本。相比"从拉普拉斯+边缘特征间接推断"，这种显式分类更可靠，也更容易调试。

改进2：pHash升级 + 分层判定

将pHash从64-bit升级到256-bit（16×16 DCT块），并对ROI做4×4网格分块：

# 伪代码
def visual_dedup(curr_roi, last_keyframe_roi):
    # 全局pHash (256-bit)
    global_dist = phash256_distance(curr_roi, last_keyframe_roi)
    if global_dist > 20:  # 明显不同，直接保留
        return KEEP
    if global_dist < 3:   # 几乎完全相同，丢弃
        return DISCARD
    # 灰色地带：做局部网格比对
    grid_curr = split_grid(curr_roi, 4, 4)
    grid_last = split_grid(last_keyframe_roi, 4, 4)
    local_dists = [phash64_distance(g1, g2) for g1, g2 in zip(grid_curr, grid_last)]
    # 超过半数网格有变化 → 内容不同，保留
    changed_cells = sum(1 for d in local_dists if d > 5)
    return KEEP if changed_cells >= 8 else DISCARD

这样既保持了CPU友好（网格pHash仍是64-bit），又通过空间分块解决了"全局布局相似但局部内容不同"的问题。

改进3：逐文本行跟踪（核心改进）

OCR返回结构化结果：每行 = (text, bbox=(x,y,w,h), confidence)。维护一个活动文本行池（Active Line Pool），记录已被识别的文本行：

# 伪代码
def track_and_dedup_lines(curr_ocr_lines, active_pool):
    new_lines = []
    for line in curr_ocr_lines:
        matched = False
        for tracked in active_pool:
            iou = bbox_iou(line.bbox, tracked.bbox)
            text_sim = normalized_levenshtein(line.text, tracked.text)
            if iou > 0.5 and text_sim > 0.85:
                # 匹配成功：更新跟踪行（多帧投票）
                tracked.update(line)  # 置信度加权投票
                matched = True
                break
        if not matched:
            new_lines.append(line)  # 新内容
    # 清理超时未更新的跟踪行
    active_pool.expire(timeout=3.0)
    return new_lines  # 仅返回新行，送入拼接

优势：行级去重不受其他行OCR错误影响；行级拼接更精准；多帧投票自然纠正OCR错误。

改进4：内容覆盖度保障（应对快速滑动）

每次OCR后，计算当前帧文本行与上一有效帧的文本重叠率：

overlap_ratio = |matched_lines| / max(|curr_lines|, |last_lines|)
  • overlap_ratio > 0.3：正常滑动，有重叠，可拼接
  • overlap_ratio < 0.3：内容空洞风险，标记为 [CONTENT_GAP]，不强行拼接
  • 输出结果中保留gap标记，供下游LLM回填时参考

这比AKS [2] 的覆盖度优化更轻量——AKS需要在选帧时优化覆盖度（需要预览未来帧），而本方案是事后检测，仅需比较相邻有效帧的OCR结果。

改进5：拉普拉斯相对阈值

维护最近K个"被判定为清晰"的帧的拉普拉斯Score滑动窗口，计算基线：

baseline = median(score_window) # 用中位数而非均值，抗异常值
is_blurry = curr_score < baseline * 0.3 # 低于基线30%判定模糊

这样阈值自动适应不同内容密度——密集文本页基线高，稀疏内容页基线低。

六、针对原始问题的直接回答

Q1: 滚动的快慢会不会影响？

会影响，但方案的处理逻辑基本正确。快速滑动时，拉普拉斯方差下降（拖影），模糊帧被过滤。当滑动停止后，清晰帧被捕获并OCR。

但有一个未被覆盖的极端情况：如果用户滑动极快，且两次停止位置之间无内容重叠（中间内容没有在任何清晰帧中出现），则这段内容永久丢失。方案无法解决这个问题——这是物理限制，任何基于抽帧的方法都无法捕获"从未清晰呈现过的内容"。

缓解措施：检测相邻有效帧的文本重叠率（改进4），标记gap，供下游处理时人工补查或LLM推断。同时在产品层面建议用户"中速匀速滑动"。

Q2: 果冻回弹（Overscroll）和往复滑动会不会影响？

原方案的pHash去重能处理大部分情况，但在文本UI上存在误判风险（见风险1）。

果冻回弹：用户滑到底部/顶部后，画面弹回原位。pHash距离会很小（回到相似位置），正确丢弃。但如果不同滚动位置的pHash距离本身就小（文本UI的布局相似性），则回弹帧和正常帧都可能被误丢弃。

往复滑动：滑下去再滑回来。pHash能识别"回到之前的位置"，但识别"回到的是哪个之前的位置"依赖文本级比对。改进3的逐行跟踪能更精准地判断"当前内容是否已在活动行池中"，避免重复OCR。

结论：原方案的pHash+文本去重组合方向正确，但pHash层需要升级（改进2），文本层需要从整帧改为逐行（改进3）。

Q3: 解决误触退出与返回会不会影响？

会影响，且有顶会先例验证可行性，但恢复不能假设100%成功。

Agent-SAMA [1] 用FSM建模移动UI状态转换，在跨App benchmark上恢复率71.9%。这意味着约28%的情况下，用户"退出再返回"后，系统无法正确恢复到之前的上下文。

方案中"挂起时记录最后一帧文本 + 恢复时anchor匹配"的思路正确，但需注意：

  • 返回时用户可能滚动到了不同位置，anchor匹配需支持部分匹配
  • 返回时可能是不同的聊天页面（如退到列表后进了另一个聊天），需通过UI分类器区分
  • 恢复失败时标记gap而非强拼，避免错误拼接

Q4: 怎么设计算法方案？

原方案的总体架构（异步流水线 + 三层去重 + 状态机）是合理的，建议在原方案基础上做6项改进（见第五节），核心改进为：

  1. 新增UI页面分类器替代间接状态推断（直接、可靠、可调试）
  2. pHash升级为256-bit + 4×4网格分层（解决文本UI区分度问题）
  3. 文本去重从整帧改为逐行跟踪（借鉴视频文本跟踪文献，鲁棒性大幅提升）
  4. 新增内容覆盖度检测（标记gap，避免错误拼接）
  5. 拉普拉斯改为相对阈值（自适应内容密度）
  6. 新增时序投票纠错（利用多帧OCR冗余提升准确率）

所有改进均在CPU上完成，新增开销约7ms/帧，不影响实时性。
