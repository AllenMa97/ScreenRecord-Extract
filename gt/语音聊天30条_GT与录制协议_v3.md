# 语音聊天 30 条 —— Ground Truth 文案与录制协议 (v3, 纯语音为主)

用途：针对 v1/v2 暴露的一个**难度稀释**问题——v1/v2 里绝大多数语音都点了"转文字"，
屏幕上直接印着正文，视觉通道(OCR)就能把答案读走，音频通道(ASR)形同虚设。
v3 把主体改成**未转写纯语音**（屏幕只有语音气泡、不出文字），并混入纯文字、
已转写语音、表情包、转账(钱包)等形态，让"视觉通道 / 音频通道"各自承担该承担的份额。

- 手机① ＝ **被录制**的那台（主视角，它发出的消息显示在屏幕右侧）
- 手机② ＝ 对端
- 共 30 条消息：① 15 条、② 15 条（即 15 个来回）

**与 v2 的形态配比差异（核心）**

| 形态 | v2 | v3 |
|---|---|---|
| 未转写纯语音（`screen_text = -`，仅音频可恢复） | 3 | **22**（含 1 条负样本） |
| 已转写语音（语音气泡 + 屏幕转文字，双通道） | 24 | 3 |
| 纯文字（仅视觉可恢复） | 3 | 2 |
| 表情包（无任何文本，不可恢复） | 0 | 2 |
| 转账/钱包（屏幕有金额文字，仅视觉可恢复） | 0 | 1 |

即 v3 里视觉通道直接可读的（V）只有 6 条，其余 24 条要么只能靠音频，要么根本无文本。

## 1. 录制协议（重要，先看这段）

1. **从空白会话开始**：先把该好友的聊天记录清空。录屏里出现的文本必须正好是这 30 条，
   混进任何别的历史消息都会污染 GT。
2. **严格按序号逐条发送**，两台手机轮流发；一条发完**收起键盘/收起语音面板**再发下一条。
3. **节奏**：每条之间停 **≥3 秒**（画面需要静止够久，管线靠静止帧建行 + 多帧投票纠错）。
4. **开勿扰模式**：任何横幅通知弹出来都会遮住一行文本，直接变成漏检。
5. **不要做**：撤回、编辑、删除、@某人、引用回复；不额外发表情/图片（本表指定的除外）。
   全程不改字号、主题、深色/浅色、护眼模式；关自动亮度、关自动旋转；室内光线稳定，避免手影。
6. **语音相关（v3 重点）**：
   - **转文字开关按本表执行**：某行 `screen_text` 不是 `-` → 发送后**点"转文字"**让它上屏；
     `screen_text = -` → **千万不要点转文字**（保留纯语音气泡，屏幕上不出任何文字）。
   - 每条语音时长 **2–6 秒**；**#27 一条 ≥12 秒**（故意让它被切成多条 ASR 段）。
   - **接收到的语音必须在 ① 上点"扬声器"外放播放**（微信默认听筒播放，录屏音轨采不到声音）；
     唯一例外是 **#26**：保持听筒/静音播放，故意让录屏音轨采不到它（负样本）。
   - 录制机媒体音量开到 ~50%，保证外放的语音能被录屏音轨采到。
7. **表情包 / 转账（#8 / #12 / #22）**：按本表位置发送一个微信默认表情、以及一笔转账
   （金额见 `screen_text`）。这两类**不要点转文字、不发语音**。
8. **一个录屏文件里连续录完三段**（别分段录，中间空窗会引入状态机噪声）：
   - ① 逐条发送 **#1–#28**。中途**不要手动滚动**——发送本身会自动把视图滚到最新（追加式滚动）。
   - ② 手动**向上滚动**翻到会话顶部，再**向下滚回**最新。慢速、分段：每滚 1–2 屏停 1–2 秒。
     这一段专门复现"同一屏幕位置被后续内容复用"的失败场景。
   - ③ 滚回最新后，再发 **#29、#30**（新消息到达 + 自动滚到底）。
9. 建议 1080p 竖屏、30fps 以上，码率别太低（糊了会掉字）。

## 4. 考点说明（相对 v2 补了什么）

| 考点 | 位置 | 想验证什么 |
|---|---|---|
| 未转写纯语音（仅音频可恢复） | #1/#2/#4/#5/#6/#9/#10/#11/#13/#14/#16/#18/#19/#20/#21/#23/#24/#27/#28/#29/#30 | 屏幕不出文字时，**ASR 通道**能否独立撑起召回；这正是 v1/v2 被"转文字"稀释掉的能力 |
| 已转写语音（双通道对照） | #7/#15/#25 | 同一条语音在"视觉+音频"两路都可达时，跨路去重(问题#1)是否生效、是否重复上屏 |
| 纯文字通道 | #3/#17 | 视觉通道单独可用性（不依赖音频） |
| 无文本消息 | #12/#22 | 表情包无任何可提取文本：**不得凭空生成文本**（负样本口径） |
| 转账/钱包消息 | #8 | 卡片上的金额文字能否被视觉通道正确读出 |
| 长语音切段 | #27（≥12s） | 一条语音被切成多条 ASR 段时，能否"一句一行"正确拆分而非粘成一条 |
| 负样本 | #26 | 未转写 + 声音未被采集：应报"检测到语音气泡但声音未采集"，**不得幻觉文本** |
| 滚动后新到达 | #29/#30 | 手动滚动回顶再回到底后，新消息是否漏采 |

## 5. GT 口径（评测时怎么算对）

- **GT = 屏幕上实际渲染出来的文字**（`screen_text` 列，逐字一致；空格/换行不敏感，评测做归一化）。
  - `screen_text = -` 的条目（未转写语音、表情包）**屏幕上没有文字**，不属于视觉可恢复集。
- **音频 GT = `spoken_text` 列**（语音真实内容），用于音频通道。
- **逐通道召回分母**：
  - 视觉通道：`V = {id | screen_text != '-'}`（本表 6 条：#3/#7/#8/#15/#17/#25）；
  - 音频通道：`A = {id | form == 'voice' and captured == 'yes'}`（本表 24 条）；
  - **最终输出（通道 A）**应覆盖 `V ∪ A` 的并集；`#26`（`captured=no` 且未转写）、
    `#12/#22`（表情包，无文本）为**不可达负样本**，不计入召回分母，只验证"不得幻觉文本"。
- 被手机状态栏/输入法/导航栏遮挡的行会从 GT 里排除，不计入召回。
- 严格一对一 P/R/F1 只在 `V ∪ A` 上计算。
- 录完把视频交给我（放到 `videos/`），我会跑管线并输出通道 A/B/C 的 P / R / F1、跟踪 ID 纯度/碎片化/ID 切换。
